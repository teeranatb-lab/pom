# Make END และการควบคุมงานตั้งแต่ Blueprint ถึงส่งมอบ
ผู้ริเริ่มแนวทาง: Teeranat Butda
สถานะ: ข้อกำหนดและบทเรียนการออกแบบ ไม่ใช่ใบรับรองระบบผลิตซอฟต์แวร์อัตโนมัติ

## เจตนาหลัก
ใช้หน้าเดียวควบคุมกระบวนการต่อเนื่อง เมื่อได้ Markdown Blueprint ต้องส่งต่อไปพัฒนา ตรวจ ทดสอบ และส่งมอบได้ ไม่จบเพียงการสร้างไฟล์ให้ผู้ใช้เอาไปสั่งงานเอง

## กระบวนการ
1. รับเจตนาและบริบท จัดเป็น Blueprint
2. ตรวจความครบถ้วน เสนอส่วนที่ขาด แล้วให้ผู้มีอำนาจตัดสินใจ
3. ล็อก Blueprint ที่อนุมัติและส่งให้เครื่องมือพัฒนา
4. ตรวจโค้ด ผลลัพธ์ และหลักฐานเทียบกับเจตนา
5. หากไม่ผ่าน ให้วิเคราะห์สาเหตุและ Root Re-entry
6. สร้างชุดส่งมอบ ทดสอบการใช้งานบนเป้าหมาย และตรวจรับ

การอนุมัติเป้าหมายไม่ได้หมายถึงอนุมัติการเผยแพร่ทุกปลายทาง การ commit, push, deploy และติดตั้งต้องอยู่ในขอบเขตสิทธิที่กำหนด

## ความรับผิดชอบในการตรวจขั้นสุดท้าย
คำแก้ล่าสุดของผู้ใช้วันที่ 6 พฤศจิกายน 2569 ให้ระบบรับผิดชอบตรวจโค้ด กระบวนงาน และผลลัพธ์ทางเทคนิคเอง ไม่โยนภาระตรวจทั้งหมดกลับให้ผู้ใช้ การอนุมัติเพิ่มหรือเปลี่ยนเจตนายังแยกจากการตรวจทางเทคนิค ดู [การสืบทอดเจตนาล่าสุด](architecture/intent-inheritance-current-state.md)

## เกณฑ์จบ
หน้าเว็บเปิดได้หรือ unit tests ผ่านเพียงบางส่วนไม่เพียงพอ ต้องมี artifact ที่ใช้ได้จริง ทดสอบทางเดินงานครบ และตรวจรับกับ Blueprint รวมถึง UI ที่อนุมัติไว้ หากไม่มีผลทดสอบให้แสดง NOT TESTED ไม่สร้างสถานะสำเร็จจำลอง

## ใช้ของเดิมก่อน
ก่อนสร้างโมดูลใหม่ให้ตรวจ Runtime และ contract ที่มีอยู่ ใช้ adapter เมื่อเชื่อมได้ วิธีคิด 18+1 เป็นคลังสำหรับเลือกแนวทางแก้ตามเจตนา ไม่ใช่เพียงรายการชื่อบนหน้า UI

## ที่มา
บทสนทนาเรื่อง OLGM Make END และการตรวจ ATI ช่วงพฤศจิกายน 2569 โดยคำสั่งวันที่ 6 พฤศจิกายนย้ำให้ใช้วิธีคิดเดิมเพื่อทำให้ coding บรรลุเจตนา ไม่เผยแพร่เนื้อหาส่วนตัวหรือที่อยู่เครื่องจากต้นทาง
