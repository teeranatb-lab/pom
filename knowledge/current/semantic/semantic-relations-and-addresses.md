# Semantic Relations และที่อยู่ของความหมาย
ผู้ริเริ่มกรอบ: Teeranat Butda  
สถานะ: สกัดข้อเสนอเชิงวิศวกรรมจาก Meaning Space Research 1.0

## ทำไมต้องมี relation ที่ระบุชนิด
ข้อความสองชิ้นใกล้กันทางเวกเตอร์อาจพูดถึงเรื่องเดียวกันแต่มีทิศทางตรงข้าม เช่น ใครเลี้ยงใคร ใครให้ใคร หรือใครมีหน้าที่ตรวจใคร การแทนทุกเส้นว่า “เกี่ยวข้องกับ” ทำให้ระบบสูญเสียโครงสร้างที่จำเป็นต่อการตอบ

ข้อเสนอในรายงานหน้า 5 ให้ Relation/Claim เก็บ:
- subject: ผู้หรือสิ่งที่เป็นต้นทาง
- predicate: ความสัมพันธ์ชนิดใด
- object: ผู้หรือสิ่งปลายทาง
- polarity: ยืนยันหรือปฏิเสธ
- modality: เกิดจริง เป็นไปได้ เป็นข้อกำหนด หรือรูปแบบอื่นตาม schema
- valid_from / valid_to: ช่วงเวลาที่ข้ออ้างใช้ได้
- evidence_id: หลักฐานที่รองรับ
- status: สถานะการตรวจและข้อขัดแย้ง

รายการนี้เป็น schema ที่เสนอในรายงาน ไม่ใช่การยืนยันว่าฐานข้อมูลที่ใช้งานอยู่มีทุกฟิลด์แล้ว

## ทิศทางและบริบท
ตัวอย่างในรายงาน “มาลีเลี้ยงสุนัขชื่อดำ” ไม่อนุญาตให้กลับเส้นแล้วตอบว่า “ดำเลี้ยงมาลี” การค้นคืนข้อความถูกแต่กลับทิศทางยังถือว่าผิด การเชื่อมหลายเส้นต้องตรวจว่าชนิดสัมพันธ์ต่อกันได้จริง ไม่ใช้ความใกล้แทนกฎอนุมาน

เงื่อนไขเวลาและขอบเขตมีความสำคัญเท่าตัวเส้น ข้อมูลที่เคยถูกต้องในพื้นที่หนึ่งหรือช่วงหนึ่งอาจใช้ตอบอีกบริบทไม่ได้

## Semantic Address
Research 1.0 อ้างแนวทาง Semantic Address จาก Atlas เป็น:
ConceptCID + RelationPath + Layer + ContextScope + EntityID + CanonicalVersion

หน้าที่คือทำให้การอ้างถึงความหมายและเส้นทางอ่านย้อนกลับได้ โดยแยกจากเวกเตอร์ค้นคืน ไม่ควรใช้ตำแหน่งบนแผนภาพ 2D แทน address นี้ เพราะภาพฉายอาจเปลี่ยนเมื่อเพิ่มข้อมูลหรือเปลี่ยนวิธีแสดง

## สถานะข้อมูล
เส้นทางนำเข้าที่เสนอคือ รอนำเข้า → โมเดลเสนอ → ผ่านตรวจโครงสร้าง → ตรวจหลักฐานแล้ว โดยมีทางแยกขัดแย้งหรือไม่ทราบ ไม่เลื่อนสถานะเป็นข้อเท็จจริงเพียงเพราะ schema ถูกต้อง

เก็บรุ่นก่อนหน้าและเหตุผลแก้ไขไว้ ข้อมูลใหม่ที่ขัดกับเก่าให้เชื่อมข้อขัดแย้ง ไม่ลบหลักฐานเก่าแบบเงียบ ๆ

## กรณีใช้
เหมาะกับคำถามเชิงผู้กระทำ–การกระทำ, กฎที่มีวันมีผล, ความสัมพันธ์ทางธุรกิจ และงานที่ต้องอธิบายว่าตัวเลขหรือข้อสรุปมาจากไหน
