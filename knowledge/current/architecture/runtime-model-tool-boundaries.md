# Runtime อิสระ และขอบเขต Model / Tool Gateway

ผู้ริเริ่มทิศทาง: Teeranat Butda  
เรียบเรียง: 8 พฤศจิกายน 2569  
สถานะ: ข้อกำหนดและการตีความสถาปัตยกรรม ไม่ใช่รายงานติดตั้งหรือทดสอบครบวงจร

## Runtime เป็นตัวควบคุมงาน

ทิศทางที่ผู้ใช้ยืนยันวันที่ 6 พฤศจิกายนคือใช้ Origin Runtime ที่มี OLGM อยู่ภายในเป็นแกน AI ไม่สร้างตัวควบคุมซ้ำอีกชุดเพียงเพื่อส่งงานระหว่างโมเดล เป้าหมายคือรักษาเจตนาและทำให้ระบบงานตามความคิดของผู้ใช้เกิดขึ้นจริง

Runtime จึงมีหน้าที่รักษาสถานะงาน ขอบเขตการกระทำ การส่งต่อ การตรวจ และการย้อนแก้ ส่วนโมเดลเป็นทรัพยากรสำหรับวิเคราะห์หรือสร้างข้อเสนอ เครื่องมือเป็นทรัพยากรสำหรับลงมือทำ การเปลี่ยนโมเดลไม่ควรทำให้กฎของงานและเกณฑ์ตรวจรับหายไป

## ความเป็นอิสระมีความหมายอย่างไร

ในบทสนทนาวันที่ 4 พฤศจิกายน ผู้ใช้กล่าวว่า “ใช่ มันต้องรันต่างหากสิ” หลังชี้ปัญหา AI ตรวจ AI แล้วไหลตามกัน และต่อมาเสนอให้เขียนเงื่อนไขตรวจเป็นโปรแกรมโดยตรง วันที่ 5–6 พฤศจิกายนยังย้ำ runtime และการใช้ของเดิม จึงไม่ควรตีความข้อความช่วงหนึ่งว่าอนุญาตให้ยกเลิกระบบควบคุมทั้งหมด

ข้อเสนอเชิงวิศวกรรมสำหรับทำความเป็นอิสระให้ตรวจได้:

- ผลของโมเดลเป็นข้อมูลเข้า ไม่ใช่คำสั่งเปลี่ยนกฎของตัวตรวจ
- โมเดลไม่แก้เกณฑ์ตรวจให้ผลงานตนเองผ่าน
- การเรียกเครื่องมือผ่านจุดตรวจสิทธิ์ที่บังคับใช้จริง ไม่อาศัยข้อความเตือนใน prompt อย่างเดียว
- ผู้ตรวจอ่าน artifact และผลทดสอบ ไม่รับเพียงคำอธิบายจากผู้สร้าง
- การเปลี่ยนสถานะงานมีหลักฐานและตรวจย้อนหลังได้

เพียงเรียก LLM คนละตัวหรือแยกชื่อ agent ยังไม่พิสูจน์ความเป็นอิสระตามข้างต้น

## Model Gateway กับ Tool Gateway

**Model Gateway** รับโจทย์ย่อยที่มีขอบเขต เลือกทรัพยากรประมวลผล ส่งบริบทเท่าที่จำเป็น และรับผลพร้อมสถานะผิดพลาด การเลือก local หรือ cloud ต้องแยกประเด็นความเร็ว ความสามารถ และขอบเขตข้อมูลออกจากกัน โมเดลที่ติดตั้งหรือแสดงชื่อในรายการไม่ได้แปลว่า inference ทำงานแล้ว

**Tool Gateway** รับแผนที่อนุญาต ตรวจชนิดการกระทำ เป้าหมาย อาร์กิวเมนต์ และสิทธิ์ ก่อนส่งให้ adapter แล้วรับหลักฐานกลับมา เอกสารที่ผู้ใช้นำมาหารือวันที่ 22 ตุลาคมเสนอ registry กลางและ adapter สำหรับ browser, desktop, files, database, OCR และ API แนวทางนี้มีคุณค่าในฐานะหลักการเชื่อมเครื่องมือ แต่ไม่ควรนำค่าตั้งโมเดลของเอกสารเก่ามาทับงาน ATI รุ่นใหม่

## การใช้ของเดิมอย่างมีหลักฐาน

ก่อนสร้าง gateway หรือ controller ใหม่ ต้องตรวจของที่มีอยู่ สัญญารับส่ง รูปแบบสิทธิ์ และวิธีเรียกใช้จริง หากเชื่อมได้ให้ทำ adapter และทดสอบการส่งต่อ ไม่คัดลอกกลไกกำกับจนเกิดหลายแหล่งตัดสินที่ขัดกัน

ต้องแยกสถานะ: พบโค้ด → เรียกโมดูลได้ → เชื่อมกันได้ → ทดสอบงานจริงครบ แต่ละระดับต้องมีหลักฐานของตนเอง ผลทดสอบ unit ของ adapter ไม่รับรองว่าระบบส่งมอบงานจริงสำเร็จ

## เกณฑ์ยอมรับที่เสนอ

ทดสอบคำขอที่มีสิทธิ์และไม่มีสิทธิ์, โมเดล timeout, เครื่องมือส่งผลไม่ครบ, หลักฐานขัดกับข้อความสรุป, การส่งซ้ำหลังผลไม่แน่นอน และการกลับไปแก้โดยรักษาเจตนาเดิม กรณีเปลี่ยนโมเดลต้องยังใช้ข้อจำกัดและเกณฑ์ตรวจชุดเดียวกับงานเดิม
