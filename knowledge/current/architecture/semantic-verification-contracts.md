# Semantic Verification: สัญญาความหมายระหว่างเจตนา แผน และผลจริง

ผู้ริเริ่มกรอบและโจทย์: Teeranat Butda  
เรียบเรียง: 8 พฤศจิกายน 2569  
สถานะ: สังเคราะห์ข้อกำหนดจากบทสนทนา ไม่ใช่ผลทดสอบระบบหรือ Canonical ฉบับใหม่

## เหตุผลที่ต้องแยกเป็นองค์ความรู้เฉพาะ

การตรวจว่าข้อมูลส่งต่อได้ ไม่เพียงพอสำหรับตรวจว่างานตรงเจตนา ข้อความ JSON อาจมีทุกฟิลด์และผ่าน schema แต่ชี้วัตถุผิด ใช้ข้อมูลผิดช่วงเวลา หรือประกาศสำเร็จทั้งที่ยังไม่ได้ปฏิบัติจริง จึงต้องเก็บความสัมพันธ์ระหว่างสิ่งที่ถูกขอ สิ่งที่อนุญาต สิ่งที่ทำ และหลักฐานของผลไว้ตลอดทาง

เอกสาร Blueprint ที่ผู้ใช้นำมาหารือวันที่ 29 ตุลาคมแยก Schema Guard, Semantic Verifier และ Domain Verifier ส่วนคำสั่งผู้ใช้วันที่ 30 ตุลาคมระบุให้ตรวจ Semantic Verification ด้วยหลักฐานจริงและรายงานเฉพาะผลที่ยืนยันได้ การแบ่งชั้นนี้ช่วยไม่ให้คะแนนของชั้นหนึ่งกลบข้อผิดพลาดของอีกชั้น

## สัญญาสามช่วง

1. **เจตนาเข้าสู่ระบบคิด**: เก็บข้อความต้นทาง ตัวตนของงาน ข้อจำกัด และบริบท ข้อความที่ตีความแล้วต้องย้อนเทียบต้นฉบับได้ ความมั่นใจของตัวแปลเป็นข้อมูลประกอบ ไม่ใช่สิทธิ์แก้เจตนา
2. **แผนเข้าสู่ระบบปฏิบัติ**: ระบุการกระทำ เป้าหมาย ขอบเขตสิทธิ์ เงื่อนไขก่อนทำ และการป้องกันทำซ้ำ ตัวปฏิบัติรับรู้หน้าจอหรือ DOM เพื่อทำงานได้ แต่ไม่เปลี่ยนเป้าหมายเอง
3. **หลักฐานกลับสู่ระบบตรวจ**: ส่งผลดิบ สถานะ เวลา และข้อมูลตรวจความคงเดิมกลับมา คำว่า SUCCESS ในผลเรียกเครื่องมือยังต้องถูกตรวจเทียบผลลัพธ์ระดับงาน

รายละเอียดนี้สรุปจาก Intent Contract, Execution Plan และ Evidence Bundle ในเอกสารที่ผู้ใช้นำมาหารือวันที่ 30 ตุลาคม ไม่ใช่การประกาศว่า contract ดังกล่าวถูกติดตั้งแล้ว

## ตรวจความสัมพันธ์ ไม่ตรวจเพียงคำคล้าย

แนวทางปฏิบัติต่อไปนี้เป็น **ข้อเสนอเชิงวิศวกรรมของการเรียบเรียง** ที่แปลงหลักการให้ตรวจได้ ไม่ใช่ข้อกำหนด Canonical ที่รับรองเพิ่ม:

- ข้ออ้างแต่ละข้อควรเชื่อมกับหลักฐานที่รองรับจริง ไม่ใช้เอกสารที่เพียงพูดถึงหัวข้อเดียวกัน
- วัตถุในคำสั่ง แผน และผลต้องเป็นวัตถุเดียวกัน เช่น แปลงข้อมูลชุดที่ได้รับ ไม่ใช่ตัวอย่างที่หน้าตาคล้าย
- ข้อจำกัดเชิงเวลา พื้นที่ หน่วย และสิทธิ์ต้องยังมีผลหลังการส่งต่อ
- ผลทดสอบต้องใช้กับ artifact รุ่นที่ส่งมอบ หากแก้ไฟล์หลังทดสอบ ต้องตรวจส่วนที่ได้รับผลกระทบใหม่
- เมื่อหลักฐานขัดกัน ให้เก็บข้อขัดแย้งและตำแหน่งที่เกิด ไม่เฉลี่ยคะแนนจนข้อขัดแย้งหาย

## ตัวอย่างตรวจสามชั้น

งานแผนที่ส่งออก CAD อาจผ่าน schema เพราะมีรายการพิกัดครบ แต่ semantic check ต้องตรวจว่ายังหมายถึงพื้นที่ที่ผู้ใช้ต้องการ ส่วน domain check ต้องตรวจ CRS หน่วย มาตราส่วน และเปิดไฟล์ได้จริง ข้อผิดพลาดด้าน CRS ไม่กลายเป็น PASS เพราะชื่อพื้นที่คล้ายกันหรือโมเดลอธิบายได้ดี

ตัวอย่างอื่น: คำสั่งให้เพิ่มฟังก์ชันโดยรักษาของเดิม ต้องมีทั้งหลักฐานฟังก์ชันใหม่และ regression check ของของเดิม จำนวนฟังก์ชันรวมที่เพิ่มขึ้นไม่พิสูจน์ว่าความสามารถเดิมยังอยู่

## เกณฑ์ทดลองที่ควรมี

กรณีถูกโครงสร้างแต่ผิดเป้าหมาย, ถูกเป้าหมายแต่หลักฐานคนละรุ่น, ผลเครื่องมือสำเร็จแต่ artifact ใช้ไม่ได้, แหล่งข้อมูลขัดกัน และผลจริงตรงข้อกำหนดครบ ทุกกรณีต้องมี expected result และหลักฐานรัน ก่อนเรียกว่า tested

สถานะเอกสารนี้: **ยังไม่ได้รันกรณีทดลองเหล่านี้** การเสนอ checklist ไม่ใช่ผลการตรวจ ATI
