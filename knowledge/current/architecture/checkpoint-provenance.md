# Checkpoint และ Provenance: ตรวจเส้นทางงานจากหลักฐาน

ผู้ริเริ่มแนวทาง: Teeranat Butda  
เรียบเรียง: 8 พฤศจิกายน 2569  
สถานะ: แนวคิดและข้อกำหนดที่พบในบทสนทนา พร้อมข้อเสนอการตรวจ ไม่ใช่ใบรับรองระบบ hash-chain

## ปัญหาที่ต้องแก้

ผู้ใช้ตั้งคำถามว่าการให้ AI ตรวจ AI อาจเกิดการคล้อยตามกัน จึงเสนอให้กระบวนการมีหลักฐานที่ตรวจจากภายนอกได้ ไม่อาศัยคำบอกเล่าว่าทำครบแล้ว หลักฐานต้องเชื่อมการเข้าจุดตรวจ การทำงาน การออกจากจุดตรวจ และการส่งต่อไปกระบวนการถัดไป

คำพูดผู้ใช้โดยตรงใน “แผนที่ Leaflet แบบโต้ตอบ”, 4 พฤศจิกายน 2569:

> ใช้ AI ตรวจ AI เดี๋ยวมันก็ไหลไปตามกัน

ในข้อความถัดมา ผู้ใช้เสนอการ hash เมื่อเข้าและออกจาก checkpoint บันทึกเวลา และให้เงื่อนไขที่เขียนเป็นโปรแกรมกำกับการผ่านขั้นตอน โดย AI รับรองตัวเองไม่ได้ วันที่ 5 พฤศจิกายนขยายให้เก็บผลการทำงานใน SQLite ทุกจุด รวมถึงเกณฑ์ที่ใช้วัดความหมาย

## สิ่งที่ checkpoint ควรพิสูจน์

การตีความเพื่อจัดระบบต่อไปนี้เป็นข้อเสนอเชิงวิศวกรรม ไม่ใช่ schema ที่ยืนยันว่าใช้งานอยู่:

- งานใดและขั้นตอนใดกำลังดำเนินการ
- รับข้อมูลและเจตนารุ่นใดเข้ามา
- ใช้เกณฑ์ตรวจรุ่นใดและเพราะอะไรเกณฑ์นั้นจึงเกี่ยวข้อง
- ทำอะไรจริง และได้ผลหรือข้อผิดพลาดใด
- หลักฐานอยู่ที่ใดและตรวจความคงเดิมอย่างไร
- ใครหรือกระบวนการใดตรวจผล และอนุญาตให้ส่งต่อหรือไม่
- เชื่อมกับ checkpoint ก่อนหน้าและผลลัพธ์ถัดไปอย่างไร

จุดสำคัญคือเก็บ **เกณฑ์ตรวจ** ร่วมกับ **ผลตรวจ** มิฉะนั้น PASS จะไม่มีความหมายเมื่อเกณฑ์เปลี่ยนหรือถูกใช้กับงานผิดประเภท

## Hash, เวลา และสิทธิ์ทำหน้าที่ต่างกัน

Hash ช่วยตรวจว่าเนื้อหาเปลี่ยนหรือไม่เมื่อเทียบกับค่าอ้างอิงที่เชื่อถือได้ การต่อ hash ช่วยตรวจการเปลี่ยนลำดับหรือข้อมูลใน chain ภายใต้แบบจำลองความเชื่อถือที่กำหนด แต่ hash ไม่ยืนยันว่าเหตุการณ์ในข้อความเกิดขึ้นจริง และผู้ที่เขียนบันทึกเท็จตั้งแต่ต้นยังสามารถสร้าง hash ที่คำนวณถูกต้องได้

เวลาในบันทึกช่วยเรียงเหตุการณ์ แต่ต้องแยกเวลาที่เครื่องกล่าวอ้างออกจากเวลาที่มีแหล่งยืนยัน สิทธิ์หรือ token ช่วยบังคับขอบเขตการทำงาน แต่ไม่ได้แทนการตรวจผลด้านความหมาย การวางทั้งสามอย่างร่วมกันจึงต้องอธิบายว่าเชื่อถืออะไรและยังไม่รับรองอะไร

## Provenance ของความคิดและผลงาน

โจทย์ในวันที่ 5 พฤศจิกายนไม่ได้หยุดที่ตรวจว่างานเสร็จ แต่รวมถึงการตรวจว่าแนวคิดหรือข้อมูลใดถูกนำมาใช้ จึงต้องแยกต้นทางมนุษย์ แหล่งอ้างอิง ข้อเสนอของโมเดล การตัดสินใจ และผลงานที่เกิดขึ้นให้ตามรอยได้

ขอบเขตที่พิสูจน์ได้คือข้อมูลและเหตุการณ์ที่ระบบเข้าถึงและบันทึกไว้ การมี checkpoint ภายนอกไม่ทำให้เห็นพารามิเตอร์ทั้งหมด กระบวนการภายในที่ไม่เปิดเผย หรือแหล่งข้อมูลการฝึกของโมเดล และไม่ใช่คำตัดสินสิทธิทางกฎหมายโดยอัตโนมัติ

## การทดสอบความน่าเชื่อถือของ chain

ข้อเสนอชุดทดสอบ: เปลี่ยน payload เก่า, ตัดรายการกลาง, สลับลำดับ, ส่งหลักฐานคนละงาน, ใช้สิทธิ์เก่าซ้ำ, ตัดการทำงานก่อนบันทึกเสร็จ และทำงานซ้ำหลัง timeout ตัวตรวจต้องบอกได้ว่าปัญหาอยู่ตรงไหน ไม่เพียงรายงานล้มเหลวรวม

การตรวจ chain ควรทำโดยเครื่องมือที่อ่านบันทึกอิสระจากตัวสร้างผล การที่ระบบ health ตอบหรือมีไฟล์ฐานข้อมูลอยู่ไม่ใช่หลักฐานว่าผ่านการตรวจเหล่านี้

## ที่มาและขอบเขต

- “แผนที่ Leaflet แบบโต้ตอบ”, 4 พฤศจิกายน 2569: ข้อเสนอ checkpoint เข้า–ออก, hash, timestamp และเงื่อนไขตรวจแบบโปรแกรมจากผู้ใช้
- “คุยหลักการ”, 5 พฤศจิกายน 2569: คำสั่งให้ runtime ตรวจการทำงาน เก็บผลแต่ละ checkpoint ใน SQLite และตรวจที่มาของแนวคิด พร้อมเกณฑ์วัดความหมาย
- ไม่ยกถ้อยคำที่ถอดเสียงกำกวมมาเป็นชื่อ protocol ไม่เผยแพร่กุญแจ ที่อยู่เครื่อง หรือเนื้อหาภายในที่สงวนไว้

เอกสารนี้ไม่มีผลรันทดสอบใหม่ สถานะความถูกต้องของระบบจริงต้องอาศัย artifact และผลตรวจที่ระบุรุ่นชัดเจน
